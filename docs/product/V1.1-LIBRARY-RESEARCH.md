The owner's Phase 3 work order (2026-11-20) placed **B-027**, **B-038** and **B-040** out of Phase 3 as V1.1 candidates: researched and kept possible, **not implemented**. This file is that research, read against the code on `open-source-gpl` (2026-11-20). Each issue's status stays in [BETA-BUG-TRACKER.md](../BETA-BUG-TRACKER.md); nothing here is a decision until the owner schedules the work (DECISIONS.md).

Phase 3 added nothing in the way of any of them: Quick View, the featured hero and Trickplay read the existing read models and change no query, schema or navigation structure.

## B-027: separate Jellyfin (and Plex) libraries beside aggregate Movies and Shows

**What exists.**
- Sources made of libraries implement `SectionedSource` (Jellyfin, Plex): their libraries are `source_section` rows, each with a kind; each catalog entry says which library it came from (`CatalogEntry.section`), and each library can be left out of the unified library (M3, docs/product/NAVIGATION.md).
- `LibraryScope.OfSource(sourceId, section)` already reads one library on its own: Sources → a server → a library is a page today (`SourceLibraryScreen`), with Details and playback scoped to it.
- Movies and Shows are the unified, aggregate views (`LibraryScope.Unified`), deduplicated by work identity across sources.

**The gap, and the one architectural change it needs.**
- **Membership is single-valued.** Jellyfin's adapter lists an item that is in two libraries once, in the first (`JellyfinSource.catalog`: "An item in two libraries is listed once, in the first"), and a version records one section. The owner's example (a Marvel library whose films are also in Movies) needs an item to belong to several libraries at once. V1.1 needs a membership relation (`section_member(source_id, section_id, item_id)` or per version), filled from every library's listing rather than the first, with the deduplication staying at the work level.
- **Navigation.** Desktop and TV: library entries in the sidebar below Movies and Shows (F-P1's collapsible sidebar is the natural home), ordered as the server orders them, hidden when a server has one library. Phone: not the bottom bar; a "Libraries" entry at the top of Movies/Shows or on the Profile page's More list.
- **Permissions, refresh, offline.** A library a user cannot see is not listed by the server, so membership follows the account (already per profile through `source.profile_id`). A library's membership refreshes with its catalog; offline, the last membership is shown (local-first).
- **Mixed libraries.** A Jellyfin "mixed" or "boxsets" library holds films and shows; its page shows both, in sections.

**Recommended V1.1 order:** the membership relation and its migration (with `ProfileIsolationTest` coverage) → scoped queries reading it → library pages in the sidebar and on phones → walks per the matrix.

## B-038: sorting and filtering Movies and Shows

**What exists.**
- Movies and Shows are ordered by title only (`ORDER BY COALESCE(metadata.sort_key, item.sort_key), item.year` in `Library.sq`).
- The data already held per work: title and sort key, year, `added_at`, provider rating, runtime, genres, watch state (watched, in progress), favourite, and per version resolution, HDR and source. Smart search (`SmartQuery`) already parses most of these as filters ("4k hdr", "unwatched", "under 2 hours", genres, decades), with its own tests.

**Approach recommended.**
- **One filter model shared with smart search**: a `LibraryFilter` (genres, decade or year range, watched state, favourites, resolution/HDR, source or library) and a `LibrarySort` (title, year, date added, rating, runtime), compiled to one parameterised query per destination. Reusing `SmartQuery`'s vocabulary keeps Search and the grids consistent.
- **Only offered where the data exists**: rating and runtime only with online metadata; resolution only where versions were measured; library only with B-027.
- **Persistence**: per profile and destination in `profile_setting` (a viewer's preference, cleared by a profile reset, not by clearing history).
- **Performance**: indexes on the sort columns used; no full reload per change (the grids are paged lazy lists already); measured on the 11,000-item fixture (`SearchPerformanceTest`'s).
- **UI**: a sort and filter bar on Movies and Shows, a sheet on phones, the controller's LB/RB unchanged (they step destinations), clear-all always visible when a filter is on.

**Dependency:** filtering by library needs B-027's membership relation.

## B-040: discovery variety on Home

**What exists (`Library.home()`).** Continue Watching, Recently Added, Favorites, Ready to Watch (unwatched by rating, at least four), Stunning in 4K HDR (smart search), franchises (provider collections), TV Shows, up to four genre rows, Movies; empty rows are omitted and no row repeats another whole.

**Limits found.**
- Nothing is personal beyond watch state and favourites: no "because you watched", no similar items.
- Recently Added has no meaning after a first scan: every work has the same `added_at`, and ties are broken by title. The same tie made the featured hero alphabetical (B-014, fixed in Phase 3 by not using that order).
- Genre rows are the library's biggest genres, not the viewer's.

**A practical direction (deterministic, explainable, no AI, no network beyond existing metadata).**
- **Because you watched X:** works sharing genres and a decade, or a provider collection, with X (the most recently completed work), at least four, excluding watched; the row names X.
- **Your genres:** genre rows ranked by the viewer's completed works rather than the library's counts.
- **Unwatched favourites**, **hidden gems** (high rating, never played, added more than 30 days ago), **next episode** (already Continue Watching's).
- **Recently Added** only when its additions differ in time (more than one scan apart); otherwise not shown.
- Rules for every row: a minimum of four, no row repeating another's first items, profile-bound reads only (`ProfileIsolationTest`), and a row's title saying why it is there.
- **Dependency:** none hard; the featured hero (B-014) should prefer a "because you watched" pick once that row exists.
