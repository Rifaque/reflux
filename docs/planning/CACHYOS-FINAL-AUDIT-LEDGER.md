# CachyOS final audit ledger (2026-11-24)

**What this is.** The record of the owner's one-shot "CachyOS final audit" session on Reflux Beta 2 (`0.9.0-beta.2`), run on the owner's CachyOS + Hyprland laptop before it is retired for Ubuntu. Issues here are `CACHY-nnn`. Where an issue is a general product bug it also has an entry in the main tracker ([BETA-BUG-TRACKER.md](BETA-BUG-TRACKER.md), B-082 onward), which stays the authority for product issues; this file does not replace it. What was run is also summarised in [VERIFICATION.md](../VERIFICATION.md), "CachyOS final audit".

**Baseline.** `main` = `origin/main` = `1d65dcf` at the start (no newer commits). The portable Beta 2 build (`reflux-0.9.0-beta.2-linux-x64`, built from `ff98a0d`) was used unmodified as the reproduction artifact; product code at `1d65dcf` is identical to it (only documentation changed after `ff98a0d`), so a development build of the baseline is the portable build's code. The owner's own data directory was never used: every run used a copy (`REFLUX_HOME`) or a fresh temporary library.

**Verification kinds are kept apart**, as in the tracker: *automated* · *physical Linux desktop (this machine, Hyprland)* · *emulator* · *physical Android/TV device* · *Windows*. This session had **no Android device, no emulator, no Android SDK and no Windows machine** (`adb devices` empty; no `ANDROID_HOME`); anything needing them is marked **Blocked (no device)**, never verified. A **GameSir G7 Pro** controller (Xbox layout, USB) was attached: Reflux's Linux reader was checked against it read-only, but its buttons need a person to press them, and no synthetic input was injected.

### CACHY-001: On Linux the window had no stable identity, so docks could not show Reflux's icon (BUG D) · B-083

- **Severity / priority / confidence:** Medium · P1 · High
- **Platform:** Linux, every desktop (found on Hyprland + XWayland) · **Component:** `desktop:app` (window class), Linux packaging
- **Reproduction:** run the portable `bin/Reflux`; `hyprctl clients -j`.
- **Expected:** a window class a desktop entry can name (`StartupWMClass`), and an entry with Reflux's icon, so a dock shows the logo and groups the window with its launcher.
- **Actual (portable Beta 2):** `class: dev-reflux-desktop-MainKt`, `xwayland: true` (the toolkit's default, from the Java main class; under the test harness the same window was `kotlin-concurrent-ThreadsKt$…`). The archive shipped no `.desktop` file; the icon (`lib/Reflux.png`) was in it but nothing pointed to it.
- **Root cause (High, verified):** Reflux set no `WM_CLASS`, and the Linux artifact had no desktop entry.
- **Fix:** `LinuxWindowClass.kt` names every Reflux window `reflux` before the first window (`XToolkit.awtAppClassName`, opened with `--add-opens java.desktop/sun.awt.X11=ALL-UNNAMED` for the packaged launcher, `run` and tests; without it Reflux runs as before and logs that the class could not be set). `bin/install-desktop-entry` (new, in the Linux archive) writes `${XDG_DATA_HOME:-~/.local/share}/applications/reflux.desktop` with `StartupWMClass=reflux`, the archive's icon, `Categories=AudioVideo;Video;Player;`, the Exec path quoted per the Desktop Entry Specification; `--remove` deletes it; a folder path containing `%` is refused with a reason (GLib's launchers look for the program before expanding `%%`, so such an entry would never start).
- **Files:** `desktop/app/src/main/kotlin/dev/reflux/desktop/LinuxWindowClass.kt` (new), `Main.kt`, `desktop/app/build.gradle.kts`, `desktop/app/packaging/linux/install-desktop-entry` (new).
- **Regression test:** `LinuxDesktopEntryTest` (3, new): the entry names the class and this folder with the specification's quoting, `--remove` removes it, a `%` path is refused, and the class is set only on Linux.
- **Before / after:** portable `dev-reflux-desktop-MainKt` → development build `reflux` for both of its windows (`hyprctl clients`, `HyprlandWalkTest` run after the fix). The entry checked with `desktop-file-validate` (valid) and opened and launched through GLib (`Gio.DesktopAppInfo`, the API GNOME-style launchers use): `StartupWMClass` read as `reflux`, and the launch ran exactly `bin/Reflux` from folders whose paths had spaces, `$`, `"`, backquotes and backslashes.
- **Packaged build (physical Linux):** `./gradlew :desktop:app:packageDesktopArchive` on this machine (a development archive at `1d65dcf`+changes, never published): `bin/install-desktop-entry` is in it and executable; `lib/app/Reflux.cfg` carries `--add-opens java.desktop/sun.awt.X11=ALL-UNNAMED`; the entry it wrote (to a scratch `XDG_DATA_HOME`) validated, and launched through GLib it started the packaged Reflux, whose window was class `reflux`, rendering Home normally on a copy of the owner's library; its log had no "could not be set" line.
- **Status:** **Fixed.** Pinning the entry in a dock and relaunching from it is **Blocked (the owner's dock)**: it needs operating Noctalia's dock and looking at it, which is the owner's screen. Procedure: run `bin/install-desktop-entry` from the extracted folder, start Reflux from the launcher, pin it, close it, start it from the pin; the icon is Reflux's and one dock item holds the window.

### CACHY-002: On Hyprland the player was two windows: a video window without controls and a controls window on a blank panel (BUG C) · B-084

- **Severity / priority / confidence:** High, release-blocking for the owner's CachyOS acceptance · P1 · High (measured on the real desktop)
- **Platform:** Linux, Hyprland 0.57.2 + XWayland, the owner's hybrid Intel/NVIDIA laptop · **Component:** `desktop:app` (`Main.kt`, `LinuxVideoShape.kt`), `ui` (`player/VideoCutouts.kt`; marks in `PlayerOverlay.kt`, `MiniPlayer.kt`)
- **History of this entry (kept honest).** The audit's first report called this "mitigated": a window rule (`opacity 1.0 override`, `no_blur`) gave a sharp player **in a nested Hyprland**. The owner then saw the real thing on the real desktop: a video window with no controls and a controls window with a blank background, and rejected the audit. The nested check had been the wrong acceptance environment; this entry records what was found on the real desktop afterwards.
- **Reproduction (real desktop):** play a film; the walk (`HyprlandWalkTest`) on a dedicated workspace of the HDMI monitor, with the session's own runtime rules neutralised.
- **Actual (before, real desktop):** the controls window's buffer reached Hyprland as **`rgb24`, without alpha**: its "transparent" areas were black, covering the picture (only a faint image showed through the compositor's 0.95 opacity), with the controls squashed into the top strip on the first frame; as a separate toplevel it floated and, on a workspace move, **stayed behind as a black panel with controls** ([player-before-real-desktop.png](cachyos-audit/player-before-real-desktop.png), [player-before-controls-left-behind.png](cachyos-audit/player-before-controls-left-behind.png); cropped to Reflux's window).
- **Root cause (measured):** not Reflux's drawing. A fifteen-line plain Java window with a clear background also came out `rgb24` and black on that XWayland, with Java 2D's XRender, X11 and OpenGL pipelines and with Skiko's software renderer, while the JDK reported per-pixel translucency supported (20 alpha-capable configurations). The session's XWayland had the NVIDIA card open as well as the Intel one; the nested one (Intel only) kept alpha. Reflux's desktop player depended on a transparent window over the video, so where a compositor gets no alpha it cannot work, and no window rule can restore alpha. The old design also made the player two toplevels, which a tiling compositor manages separately (floating, blur, workspaces).
- **Why the rule did not help:** opacity and blur rules change how the compositor blends a window's alpha; a window with none stays opaque black (opacity 1.0 only makes it more so).
- **Options weighed (the owner chose B):** A, the controls window shaped to its controls (no alpha needed, still two windows, workspace problem left); **B, one window: the video surface shaped around controls drawn beneath it**; C, video rendered by Compose through libmpv's render API (a GL or software-copy rewrite).
- **Fix (B):** on Linux the video surface (libmpv's X11 window inside a heavyweight `Canvas`) is the main window's own native child in its layered pane, placed at the bounds Compose gives the video stage (not a `SwingPanel`: measured, Compose draws nothing in a `SwingPanel`'s area, so controls beneath could never be seen). The controls are composed in the main window beneath the surface over black, as Android composes its player over its surface. Each element drawn over the picture reports its bounds (`Modifier.cutsVideo()`, collected by `LocalVideoCutouts`, provided only by the Linux shell); `LinuxVideoShape` sets the surface's **bounding** shape to the surface minus those areas and its **input** shape to nothing (X SHAPE through libXext), re-applies it on every reshape, and has the window draw again so what a hole uncovers is painted at once. Windows keeps the `SwingPanel` and its controls window; Android is unchanged.
- **Files:** `desktop/app/src/main/kotlin/dev/reflux/desktop/LinuxVideoShape.kt` (new), `Main.kt`; `ui/src/commonMain/kotlin/dev/reflux/ui/player/VideoCutouts.kt` (new), `PlayerOverlay.kt`, `MiniPlayer.kt`; tests `LinuxVideoShapeTest.kt`, `VideoCutoutsTest.kt` (new), `EmbeddedPlaybackTest.kt`, `MiniPlayerWindowTest.kt`, `PlayerChromeResizeTest.kt`, `WindowHarness.kt`, `HyprlandWalkTest.kt`.
- **After (real desktop, a test workspace on the HDMI monitor; captures of Reflux's window only, taken only while that workspace was shown):** playing tiled ([player-after-real-desktop.png](cachyos-audit/player-after-real-desktop.png)), floating, resized, paused, seeked, fullscreen ([player-after-fullscreen.png](cachyos-audit/player-after-fullscreen.png)) and back, moved to another workspace and back ([player-after-workspace-return.png](cachyos-audit/player-after-workspace-return.png)), the mini-player ([player-after-mini-player.png](cachyos-audit/player-after-mini-player.png)): **one window in every state** (`hyprctl clients`: no second Reflux window at any step; on the workspace move only the player moved, and nothing was left), the picture sharp, the controls over it. The owner's monitors were recorded and restored around every run (eDP-1 on 5, HDMI-A-1 on 4).
- **Look:** where controls show, the picture is cut away and they are drawn over black rather than over a translucent scrim on the picture; elsewhere the picture is whole; hidden controls leave the whole picture.
- **Status:** **Fixed (physical Linux), then superseded on Linux by CACHY-011**: the owner rejected the black-band look; the shaped native window stays only as the labelled fallback (`linux-x11-shape-fallback`) for when the integrated picture cannot be set up. The owner's own check of the complete playback experience is the acceptance and is pending.

### CACHY-011: The Linux picture drawn by Compose through libmpv's render API, with the controls over the real video (the owner's brief, "Replace the Linux Black-Band Player") · B-084

- **Severity / priority / confidence:** High (the owner's acceptance of the Linux player) · P1 · High for the path, rendering, lifecycle and memory (measured on the real desktop); Medium for power (RAPL is root-only here; not measured)
- **Platform:** Linux only (Skiko draws with GLX); Windows and Android unchanged · **Component:** `playback/mpv` (`MpvGlRender.kt` new: libmpv's render API; `MpvPlayer.property`), `desktop:app` (`LinuxGlVideo.kt`, `SkikoGl.kt`, `GlibcTrim.kt` new; `DesktopPlatform.kt`, `Main.kt`)
- **Why:** CACHY-002's single window cut the picture away under the controls (black bands, an opaque panel). The owner asked for the picture to stay visible under a natural gradient, the controls composed over it, with no second window, no CPU read-back and no silent fallback.
- **Design (verified against Skiko 0.150.1 and libmpv 0.42's installed `render.h`/`render_gl.h`):** Skiko draws Reflux's window with OpenGL through GLX on the event thread. Inside Compose's draw of the video stage, with Skiko's context current, libmpv renders the frame through a framebuffer into a texture in **that same context**; Skia adopts the texture (`Image.adoptTextureFrom`) and draws it like any image; the existing player overlay (scrims, title, timeline, menus, subtitles) is composed over it as on Android. One context, one thread, no cross-context sharing, no read-back. libmpv's update callback only asks for a redraw (a Compose state read where the picture is drawn); `BLOCK_FOR_TARGET_TIME` is 0, so the event thread never waits for a frame; after libmpv's GL calls Skia's cached GL state is reset.
- **Ownership:** Skiko owns the context. The texture is made in it and adopted by Skia, which deletes it with its image; it and its framebuffer (Reflux's, deleted by Reflux in the context) are kept across playbacks of one size and remade on resize or when Skiko replaces its context. The render context belongs to the playback: made **before the engine opens a file** (`LinuxGlVideo.attach`, which waits for a draw and forces one with Skiko's public `Redrawer.renderImmediately` if none comes) and freed in a draw, context current, before the engine is closed (`release`, also forcing a draw if none comes; outside a draw only for a window being disposed, logged). The update callback is detached before the render context is freed; JNA callbacks are held for its whole life.
- **Skiko's internals** are reached in one adapter, `SkikoGl` (SkiaLayer → `redrawerManager` → `getRedrawer()` → `contextHandler` → `context`), each step checked (the layer's public `renderApi` must be `OPENGL`, the redrawer `LinuxOpenGLRedrawer`); nothing is cached across draws; `SkikoGl.TESTED_VERSION` = 0.150.1, and a unit test fails when Skiko changes so the path is checked again. Where any step fails the playback uses the fallback and the log says why.
- **Renderer identifiers in the diagnostics log:** `Video renderer: linux-mpv-gl-integrated (…, vo=libmpv, hwdec=…)` or `Video renderer: linux-x11-shape-fallback (reason)`, with the render-context and texture lines, a decoding report after 120 frames (`hwdec-current`, `current-vo`, formats, colour matrix and range, drops, A/V sync) and a release line (frames, draws, libmpv updates). `REFLUX_NATIVE_VIDEO_WINDOW=1` forces the fallback for comparison; `REFLUX_RENDER_HWDEC` overrides decoding for measurement.
- **Found and fixed while verifying (each measured, not assumed):**
  1. *The renderer was chosen before the window existed* and the empty answer was kept, so the first run silently used the fallback: now resolved when first needed with a window.
  2. *Upside down* (texture read with a bottom-left origin): libmpv's row 0 is the frame's top in an FBO; now `TOP_LEFT`, checked with the test card's timecode.
  3. *Sound without picture, once on the real desktop:* the render context was made at the first draw after the engine was handed over; when the file opened first, libmpv's video output failed and it played audio only (`current-vo` empty, 1 frame in 24 s). Now the context exists before the file opens; the log order shows it for every playback since.
  4. *Decoding on the wrong GPU:* mpv's own order chose `nvdec-copy` (NVIDIA decodes, frames copied to the Intel GPU that draws, waking the dGPU). Now `vaapi-copy` first on Mesa, `auto-safe` on NVIDIA's OpenGL (`DesktopPlatform.renderedHwdec`).
  5. *Memory after each playback* (~12 MB, all anonymous memory, Java heap flat): measured by mapping kind; not GPU mappings; unchanged by a separate libmpv context (built, measured, reverted) or by reusing the texture; glibc's per-thread arenas keeping the copy-back frame pools. `malloc_trim(0)` after the engine closes: 20 playbacks now stay within 589–760 MB, creeping ~4–5 MB per playback like the native-window path.
- **Decoding (the limit, measured):** with Skiko's GLX context on Mesa, mpv's zero-copy VA-API interop is impossible (it needs EGL): `hwdec=vaapi` gives `hwdec-current=no` (software). So on this laptop the integrated path decodes in hardware **with a copy back through system memory** (`vaapi-copy`); the native window used zero-copy `vaapi`. With Skiko on NVIDIA's OpenGL (PRIME offload, environment only) mpv uses **zero-copy `nvdec`** (`dec-format=cuda`): the architecture hands frames over without a copy wherever the driver has an interop mpv supports with GLX.
- **Measurements (real desktop, HDMI test workspace, 20 s each, test patterns encoded with NVENC):**

  | File | Path | Decoder | Dropped | A/V | CPU (of one core; 20 cores) | Intel busy (idle 3%) | NVIDIA |

  | 1080p H.264 | integrated | vaapi-copy | 0 | 0.000003 | 23% | 55% | dec 0% |
  | 1080p HEVC | integrated | vaapi-copy | 0 | 0.000004 | 21% | 55% | dec 0% |
  | 4K HEVC | integrated | vaapi-copy | 0 | 0.000002 | 42% | 59% | dec 0% |

- **Pictures (the owner's real desktop, Reflux's own window only, final build):** playing with controls ([integrated-playing.png](cachyos-audit/integrated-playing.png)), controls hidden ([integrated-controls-hidden.png](cachyos-audit/integrated-controls-hidden.png)), a dark scene with controls ([integrated-dark-scene.png](cachyos-audit/integrated-dark-scene.png)), the speed menu open ([integrated-menu-open.png](cachyos-audit/integrated-menu-open.png)), resized ([integrated-resized.png](cachyos-audit/integrated-resized.png)), fullscreen ([integrated-fullscreen.png](cachyos-audit/integrated-fullscreen.png)), the mini-player ([integrated-mini-player.png](cachyos-audit/integrated-mini-player.png)). Orientation, aspect (pillarbox and letterbox), BT.709 limited range and the gradient were checked on them; paused, sought, floating, workspace move and back were walked too. One Reflux window in every state.
- **Tests:** `MpvGlRenderTest` (2, real libmpv: without OpenGL the render context is refused, the reason kept, the engine still closes; properties readable); `LinuxGlVideoTest` (5: decoding policy, engine options, no Skia layer → not available and why, identifiers, the Skiko version pin); opt-in window tests `IntegratedPlayerLifecycleTest` (N playbacks, each paused, resumed, sought, fullscreen and back, one closed on a hidden workspace; every render context made is released, nothing fails, memory levels off) and `IntegratedPlayerPerfTest` (the table above); `HyprlandWalkTest` gained controls-hidden, dark-scene and menu steps and keeps the diagnostics log; `EmbeddedPlaybackTest` and `MiniPlayerWindowTest` branch for a picture drawn in the window (`Shell.integratedPicture`).
- **The mini-player's corners (the owner's report after testing, 2026-11-24):** the dock's card was rounded but the video in it kept square corners. The video canvas had no clip; only the controls over it had the dock's shape (`pictureRim`, which also draws the native surface's corner arcs). ### CACHY-003: Quick View waited for every episode of a long show (BUG B) · B-082

- **Severity / priority / confidence:** Medium · P1 · High
- **Platform:** all (shared UI); measured on Linux · **Component:** `ui` (`QuickView.kt`, `Models.kt`), `library` (`Library.showOutline`)
- **Reproduction:** open Quick View (X, right-click, long touch) on *The Vampire Diaries* (8 seasons, 171 episodes) or *The Originals* (5 seasons, 92 episodes).
- **Expected:** the summary at once.
- **Actual:** Quick View drew nothing until it had built the **whole details page model**: a `LibraryEntry` (artwork, watch state, metadata, availability) for the show, every season and every episode, a card for every episode, the cast, and version choices. It shows none of that per-episode detail. The cost grows about 1 ms per episode on this desktop, and every library change during the read restarts it.
- **Measurement (method):** (1) `QuickViewTimingTest` (opt-in, `REFLUX_TIMING_LIBRARY` = a checkpointed copy of the owner's library), 5 runs per show, same JVM; (2) `QuickViewWalkTest` (opt-in, real shell on a copy of the owner's data directory, its startup sync included), from `openQuickView` until the pane's favourite button is in the semantics tree, polled every 80 ms, cold then two warm rounds. The first shell runs showed exactly 3,000 ms: an artifact of the walk's window sitting on a hidden workspace, which gets no frame callbacks; all figures below are with `-Dskiko.vsync.enabled=false`, before and after alike.

| Show (episodes) | Model before | Model after | Shell before: cold / warm / warm | Shell after: cold / warm / warm |
| --- | --- | --- | --- | --- |
| The Vampire Diaries (171) | 143–161 ms | 6–7 ms | 813 / 242 / 243 ms | 202 / 81 / 84 ms |
| The Originals (92) | 77–84 ms | 4–5 ms | 169 / 167 / 165 ms | 109 / 81 / 81 ms |
| Suits (42) | 39–41 ms | 3 ms | 81 / 82 / 81 ms | 82 / 86 / 85 ms |

  Shell figures of about 80 ms are the poll interval: the pane appeared within one poll. These are a fast desktop CPU (Arrow Lake); the owner's 5–6 s was on slower hardware (tablet, Fire TV), where the same per-episode work is many times slower. No Android or TV device was attached, so the device figure is **not measured** here.

### CACHY-007: Android: a film sometimes plays in a small box with black on all four sides (BUG E) · B-088

- **Severity / priority / confidence:** Medium · P2 · Low (not reproduced)
- **Platform:** Android phones (reported) · **Component:** `android/app` (`MainActivity.VideoLayer`, `Media3Player`)
- **Reproduction:** **Blocked (no device)**: no Android device, emulator or SDK on this machine.
- **Code analysis:** the picture is laid out at its own shape (`width × pixelWidthHeightRatio / height`), centred, with the buffer fixed at the video's size (`setFixedSize`). A correctly flagged film is therefore boxed on two sides at most (bars top and bottom on a phone held upright). Black on all four sides means the picture is smaller than its box both ways: either the file has bars of its own (a windowboxed encode, then correctly pillarboxed again) or the surface's fixed size disagrees with what the decoder renders (rotation or crop metadata). The code cannot tell which; the device can.
- **Not done blind:** a pinch or zoom control over the `SurfaceView` under the shared player overlay changes touch routing that cannot be tested here.
- **Procedure for the device:** a screenshot; `adb shell dumpsys SurfaceFlinger` (the video layer's buffer and display size); `ffmpeg -i <file> -vf cropdetect -frames:v 300 -f null -` on the same film. Bars in the file: a zoom-to-fill control. A size mismatch: a surface fix with its own test.
- **Status:** **Blocked (no device).**
